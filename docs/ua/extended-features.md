# Можливості понад вимоги завдання

Завдання вимагає створення, редагування й видалення залів, пошуку доступності, бронювання, тарифних правил, документації, безпеки та корисних звітів. Рішення додає наведені нижче можливості, щоб основний функціонал був практичним і придатним до розширення.

## Користувачі, ролі та дозволи

Common містить бізнес-моделі `User`, `Role`, `Permission`, `RolePermission` і контракти репозиторіїв. DAL містить persistence entities, заповнення через readers та профілі AutoMapper. Явний DAL reference seeder створює стабільного системного користувача та пов'язує його з роллю `Registered` і дозволами читання та запису залів і бронювань.

Контролер бронювання зараз призначає бронювання попередньо створеному користувачу, оскільки реєстрація та автентифікація не входили до переліку потрібних методів API. Моделі готують систему до подальшої integration із системою ідентифікації, але зараз **не** забезпечують авторизацію контролерів. Перед використанням у промисловому багатокористувацькому середовищі потрібно додати автентифікацію та політики дозволів.

## Read Endpoints і посторінкове виведення

Окрім п'яти обов'язкових операцій, API надає деталі залу, посторінковий список залів і посторінковий список бронювань. Вони потрібні для адміністрування, отримання згенерованих ідентифікаторів і запобігають необмеженим відповідям із колекціями.

## Звіти й аналітика

`GET /api/v1/reports/bookings-summary` повертає загальну кількість бронювань, дохід, валюту та кількість і дохід у розрізі залів. Application обробляє дані обмеженими сторінками, а не завантажує всю таблицю в пам'ять.

## Автоматизація життєвого циклу

Бронювання мають стани `Reserved`, `Rejected`, `Completed` і `Cancelled`. Фонове завдання Quartz атомарно переводить прострочені резервування у стан `Completed` обмеженими пакетами й журналює фактичну кількість змінених рядків. Один запуск використовує спільний UTC cutoff. `BackgroundJobs:CompleteBookings:Enabled=false` вимикає планування; тестові fixtures встановлюють це автоматично.

## Версіонування та документація API

Версіонування через URL (`/api/v1`) дозволяє майбутнім контрактам співіснувати. Swagger/OpenAPI генерується для версій у середовищі розробки, а кореневий URL перенаправляє на Swagger.

## Валідація та обробка помилок

Окремі валідатори FluentValidation перевіряють обмеження вхідних даних, що не залежать від стану застосунку, а managers перевіряють правила, яким потрібен цей стан. Очікувані помилки використовують `Result`, а middleware API формує контрольовані відповіді для помилок перевірки та неочікуваних винятків без розкриття трасування стека.

## Спостережуваність

Serilog створює структуровані журнали запитів і застосунку. Docker Compose містить Seq, тому журнали можна шукати й аналізувати без додаткового налаштування. Handler доменної події рівня Services журналює створення бронювання.

## Явне початкове налаштування бази

Startup initialization за `DatabaseSeeding:Enabled=true` спочатку застосовує потрібні scripts, потім data seeding. Початкову схему створюють зовнішнім code-first налаштуванням, додають процедури та обов’язкові довідкові дані, потім генерують повторно використовуваний setup-скрипт із бази. Репозиторій не містить code-first context або deployment-tool project. Необов’язковий demo seeder створює Hall A, Hall B і Hall C зі стабільними IDs.

## Розширена перевірка

Рішення розділяє Common unit tests, BLL unit tests, BLL integration tests і Services Web integration tests. SQL Server Testcontainers перевіряють реальні зіставлення та запити. Колекція у `test/Postman/` динамічно створює майбутню дату та унікальні назви, передає ідентифікатори й багаторазово перевіряє всі п'ять операцій API без ручної зміни даних.

## Операційна основа

Docker Compose надає API і Seq; база даних — віддалений SQL Server. SQL Server контейнери використовуються лише в integration tests. Час зберігається в UTC, TimeProvider ізолює залежність від часу.
