# Рефакторинг на layered architecture

Проєкт перенесено з попередньої структури, орієнтованої на Clean Architecture і CQRS, до явної layered architecture. Поточне рішення містить чотири робочі проєкти та чотири тестові проєкти; застарілі каталоги `Api`, `Application`, `Domain` та `Infrastructure` видалено з репозиторію.

## Відповідність поточних проєктів рівням

| Проєкт | Рівень | Відповідальність |
| --- | --- | --- |
| `BookingApp.Services.Web` | Service | Контролери MVC, DTO HTTP, middleware, конфігурація, dependency injection, Swagger, фонові завдання, початкові дані та handlers доменних подій. |
| `BookingApp.Bll.Common` | Common | Бізнес-моделі, об'єкти-значення, інтерфейси managers і репозиторіїв, помилки, результати та контракти доменних подій. Не залежить від ASP.NET Core або EF Core. |
| `BookingApp.Bll` | BLL | Сервісні managers, ціноутворення, створення періоду бронювання, валідатори FluentValidation і зіставлення бізнес-моделей із моделями читання BLL. |
| `BookingApp.Dal.PostgreSQLRepositories` | DAL | Контекст EF Core, репозиторії PostgreSQL, сутності збереження, конфігурації сутностей, зіставлення AutoMapper і міграції. |

Напрям залежностей під час компіляції:

```text
Services.Web ──> Bll ──> Bll.Common
      │                     ▲
      └──> Dal.PostgreSQLRepositories ──┘
```

`Services.Web` є коренем композиції та єдиним проєктом, який реєструє конкретні реалізації.

## Основні зміни

### Managers замість handlers запитів

MediatR, Commands, Queries і handlers запитів видалено. Контролери викликають `IBookingManager`, `IConferenceHallManager` та `IReportManager`. Managers надають цілісні бізнес-операції та отримують абстракції репозиторіїв й інші бізнес-сервіси через dependency injection.

### Окремі представлення на межах рівнів

- Common містить анемічні бізнес-моделі та моделі вхідних даних операцій.
- DAL містить сутності EF Core, які успадковують призначений лише для збереження базовий клас `Entity`.
- Services містить DTO запитів і відповідей HTTP.
- Профілі AutoMapper належать рівню, який виконує перетворення: Services зіставляє DTO HTTP, BLL створює моделі читання, а DAL зіставляє бізнес-моделі із сутностями збереження.

### Контролери MVC

Групи Minimal API замінено версіонованими контролерами ASP.NET Core MVC. Контролери залежать від інтерфейсів managers та `IMapper` і не звертаються безпосередньо до репозиторіїв або EF Core. Маршрути `/api/v1` і структура відповідей збережені.

### Перевірка вхідних даних

Статичний `ManagerInputValidator` замінено окремими валідаторами FluentValidation для операцій у BLL. Моделі вхідних даних Common використовують `DateOnly` і `TimeOnly`, тому managers не отримують час як рядок. Services знаходить усі публічні валідатори BLL через assembly discovery. У managers залишилися правила, яким потрібен стан застосунку: наявність залу, перетин бронювань, підтримка послуг і перевірка минулого часу.

### Явне збереження змін

Попередній `EntityChangeTracker` неявно копіював змінені моделі Common у сутності EF перед збереженням. Його видалено. Репозиторії тепер мають явні операції `Update`, зіставляють зміни із сутностями, знайденими EF Core, і зберігають їх через `IUnitOfWork`. Базовий репозиторій упорядковує сторінки безпосередньо за спільним ідентифікатором сутності DAL і не має зайвих абстрактних hooks для впорядкування або отримання ідентифікатора моделі.

### Зіставлення та dependency injection

Ручні методи `ToModel` у managers замінено профілем AutoMapper рівня BLL. Services виконує єдину реєстрацію профілів AutoMapper для Services, BLL і DAL. FluentValidation використовує assembly discovery, а managers, репозиторії, диспетчер доменних подій і фонові завдання реєструються явно в корені композиції.

### Тести та структура репозиторію

Усі тестові проєкти та матеріали Postman розміщено в `test/`. Підтримуються набори `BookingApp.Bll.Common.UnitTests`, `BookingApp.Bll.UnitTests`, `BookingApp.Bll.IntegrationTests` і `BookingApp.Services.Web.IntegrationTests`. Архітектурні тести перевіряють конфігурацію AutoMapper, правила сутностей DAL, залежності контролерів, серіалізацію запитів і передачу доменних подій. Застарілі каталоги збірки попередніх проєктів видалено.

### Вплив на міграції бази даних

Історію міграцій об'єднано в поточну початкову міграцію. Локальні бази, створені старим ланцюжком міграцій, несумісні з новою історією. Одноразові бази середовища розробки потрібно створити заново; для промислових даних слід підготувати послідовну міграцію або узгодити історію міграцій замість видалення бази.

## Результат

Після рефакторингу рішення має явні межі рівнів, потік від контролера до manager, видимі операції збереження, централізовану композицію, окремо тестовану бізнес-логіку та не залежить від Pipeline посередника. Поведінку API й обов'язкові бізнес-можливості збережено.
