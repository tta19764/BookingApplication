# Можливості понад вимоги завдання

Завдання вимагає створення, редагування й видалення залів, пошуку доступності, бронювання, тарифних правил, документації, безпеки та корисних звітів. Рішення додає наведені нижче можливості, щоб основний функціонал був практичним і придатним до розширення.

## Користувачі, ролі та дозволи

Domain та Infrastructure містять моделі `User`, `Role`, `Permission`, `RolePermission`, repository і EF Core mappings. Development seeding створює стабільного системного користувача та пов'язує його з роллю Registered і дозволами читання/запису залів та бронювань.

Endpoint бронювання зараз призначає бронювання seeded-користувачу, оскільки registration та authentication не входили до переліку потрібних API методів. Моделі готують систему до подальшої identity-інтеграції, але зараз **не** забезпечують endpoint authorization. Перед production-використанням як багатокористувацького API потрібно додати authentication і permission policies.

## Read endpoints і pagination

Окрім п'яти обов'язкових операцій, API надає деталі залу, посторінковий список залів і посторінковий список бронювань. Вони потрібні для адміністрування, отримання згенерованих ID та запобігають необмеженим відповідям із колекціями.

## Звіти й аналітика

`GET /api/v1/reports/bookings-summary` повертає загальну кількість бронювань, дохід, валюту та кількість/дохід у розрізі залів. Application обробляє дані обмеженими сторінками, а не завантажує всю таблицю в пам'ять.

## Автоматизація життєвого циклу

Бронювання мають стани Reserved, Rejected, Completed і Cancelled та доменні події. Quartz background job знаходить завершені в часі активні бронювання обмеженими пакетами й автоматично переводить їх у Completed.

## Версіонування та документація API

Версіонування через URL (`/api/v1`) дозволяє майбутнім контрактам співіснувати. Swagger/OpenAPI генерується для версій у Development, а кореневий URL перенаправляє на Swagger.

## Валідація та обробка помилок

FluentValidation і MediatR pipeline централізують перевірку вводу. Application/Domain failures використовують Result, а API middleware формує контрольовані відповіді й не розкриває stack traces.

## Спостережуваність

Serilog створює структуровані request та application logs. Docker Compose містить Seq, тому логи можна шукати й аналізувати без додаткового налаштування. Handlers доменних подій логують життєвий цикл бронювання.

## Seed data та повторюваний startup

Development startup застосовує migrations та ідемпотентно створює ролі, permissions, seeded-користувача й три потрібні зали. Стабільний user ID і згенеровані hall IDs дозволяють передбачувані локальні сценарії без hard-coded database rows у клієнтах.

## Розширена перевірка

Рішення розділяє Domain unit, Application unit, Application integration та API integration tests. PostgreSQL Testcontainers перевіряють реальні mappings і queries. Collection у `test/Postman/` динамічно створює майбутню дату та унікальні назви, передає IDs і багаторазово перевіряє всі п'ять API операцій без ручної зміни даних.

## Операційна основа

Docker Compose надає API, PostgreSQL і Seq. Конфігурація розділена за environments, timestamps зберігаються в UTC, а `IDateTimeProvider` робить залежну від часу поведінку тестованою.
